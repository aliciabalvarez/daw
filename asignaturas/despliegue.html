    Implantación de arquitecturas web.

    Qué es una arquitectura web y cómo ha evolucionado. Después, cómo instalar y arrancar el servidor web Apache y el servidor de aplicaciones Tomcat. Por último, cómo se organiza y se despliega una aplicación web Java: archivos WAR y descriptor de despliegue web.xml.

    1.- Aspectos generales de arquitecturas web.

    La WWW (World Wide Web) funciona así: el navegador (web browser) pide un recurso a un servidor y este se lo devuelve en un formato estándar. Gracias a esos estándares, cualquier navegador puede hablar con cualquier servidor.

    Mecanismo estándarQué significa
    Modelo estándar de nombresTodo servidor y todo contenido se identifica con una URL (Uniform Resource Locator), es decir, su “dirección”.
    ContenidoCada contenido lleva indicado su tipo (HTML, imagen, PDF…) para que el navegador sepa cómo interpretarlo.
    Formatos de contenidos estándarTodos los navegadores entienden los mismos formatos: HTML, ECMAScript/JavaScript, etc.
    Protocolos estándarReglas de comunicación comunes. El más usado es HTTP (Protocolo de Transferencia de HiperTexto), que funciona sobre TCP/IP.
    Ojo con los apuntes

    Los apuntes dicen que el protocolo más usado es “HTML (Protocolo de Transporte de HiperTexto)”. Es una errata: el protocolo es HTTP (HyperText Transfer Protocol). HTML es el lenguaje de marcas con el que se escriben las páginas.

    Organismos de estandarización

    OrganismoQué estandariza
    W3C (World Wide Web Consortium)HTML, CSS, XML y el protocolo SOAP (intercambio de mensajes XML entre procesos).
    WHATWGEvolución de HTML, junto con el W3C.
    IETF (Internet Engineering Task Force)Protocolos de Internet: HTTP, SMTP (correo) y TCP/IP.
    ICANNAsigna nombres de dominio y direcciones IP. No define tecnologías web, pero garantiza que los dominios sean únicos.
    Ecma InternationalECMAScript, el estándar en el que se basa JavaScript.
    ISOEstándares de TIC en general; no solo web.
    ITUTelecomunicaciones e infraestructura de red.

    Aspectos a destacar en una arquitectura web

    • Escalabilidad: poder crecer si aumentan los usuarios.
    • Separación de responsabilidades: cada parte hace una sola cosa.
    • Portabilidad: poder llevarla a otro sistema.
    • Uso de componentes en los servicios de infraestructura.
    • Gestión de las sesiones del usuario.
    • Aplicación de patrones de diseño.

    ElementoPapel

    2. ConsumidorAccede al servicio para usarlo.

    1.1.- Evolución de los servicios web.

    El uso de servicios web ha crecido junto con Internet, gracias a estos factores:

    • El contenido es más dinámico: hay que combinar datos de fuentes muy distintas al instante.
    • El ancho de banda es más barato: se puede servir vídeo y audio.
    • El almacenamiento es más barato: hay que gestionar grandes cantidades de datos.
    • La computación extendida (móviles, tabletas…): el ordenador ya no es el dispositivo principal, así que el servicio debe funcionar en cualquier dispositivo, navegador y conexión. Por eso ganan importancia formatos neutros como XML.

    En una organización se suele empezar por servicios simples que, poco a poco, se integran en otros más complejos.

    FaseÉpocaCaracterísticaEjemplo
    Web 1.0Años 90Estática y de solo lectura. El usuario solo consulta.Páginas informativas
    Web 2.0Principios de los 2000Interacción y colaboración: el usuario crea y comparte contenido.Facebook, blogs, wikis, YouTube
    Web 3.0Desde 2010Web semántica: las máquinas “entienden” el significado de los datos (IA, recomendaciones, búsqueda semántica).Recomendaciones personalizadas
    Web 4.0FuturoAún sin definir: IA, IoT (Internet de las cosas) y unión de la web con el mundo físico.Automatización, salud, movilidad

    1.2.- Tecnologías asociadas a las aplicaciones web.

    Las aplicaciones web usan páginas dinámicas: el servidor las genera y el navegador las muestra. Además, la página puede traer código (normalmente JavaScript) que ejecuta el propio navegador. Por eso hay tecnologías del lado servidor y del lado cliente.

    TecnologíaDónde se ejecutaClaves
    ASP (Active Server Pages)Servidor“Páginas activas” de Microsoft, pensadas para su servidor IIS. Generan el resultado a medida de cada petición (p. ej., un buscador). También hay versiones para Unix/Linux.
    CGI (Common Gateway Interface)ServidorUno de los estándares más antiguos para pasar datos de una página al servidor (formularios, buscadores, foros…). Se suele programar en Perl o en C.
    CSS (Cascading Style Sheets)ClienteDa formato a las páginas. Separa el contenido de la presentación: un cambio en la hoja afecta a todas las páginas enlazadas.
    JavaServidorLenguaje de referencia en Java EE, Spring o Grails. Multiplataforma y orientado a objetos (módulos independientes que se amplían fácilmente). Lo creó Sun Microsystems, lo liberó bajo GNU GPL y ahora es de Oracle.
    JavaScriptClienteInterpretado por el navegador: menús, animaciones, juegos… Se prefiere a VBScript porque lo aceptan muchos más navegadores.
    PHP (Hypertext Preprocessor)ServidorParecido a ASP. Muy eficiente con bases de datos como MySQL; muy usado en páginas dinámicas complejas.
    VBScriptCliente o servidorLa respuesta de Microsoft a JavaScript, solo para Internet Explorer. En el servidor, el cliente recibe el resultado, no el código.
    Pista

    El código del servidor (PHP, ASP, Java…) nunca llega al navegador; solo llega el HTML que genera. El código del cliente (JavaScript, CSS) sí se descarga y puedes verlo con “Ver código fuente”.

    Autoevaluación

    ¿Podemos ver una página web sin que intervenga un servidor web?

    Sí. Un .htm, .html o .xhtml guardado en tu equipo se abre directamente con el navegador. El servidor web solo hace falta para enviarte la página por la red.

    1.3.- Tipos de aplicaciones web.

    Una aplicación web es una plataforma que automatiza los servicios que se ofrecen a los usuarios: tienda online, reserva de vuelos, simulador de hipotecas… Clasificarlas es difícil porque hay muchísimas. Hay dos criterios.

    Según cómo se presenta y qué contenido muestra

    TipoDescripción
    EstáticaEscrita en HTML. Puede tener elementos en movimiento (banners, GIF animados, vídeos), pero su contenido no cambia.
    AnimadaHecha con tecnologías de animación (como Flash). Diseños muy creativos, pero esta tecnología está descontinuada: los navegadores la bloquean por sus vulnerabilidades.
    DinámicaHecha con lenguajes como PHP o ASP. La estructura de la página y el contenido van separados, y el código inserta el contenido en la estructura. Suele gestionarse desde un panel de control.
    PortalSu página principal da acceso a muchas secciones: foros, chat, correo, buscador, noticias, zona registrada…
    Con gestor de contenidosEl administrador actualiza el contenido desde un panel de gestión sencillo. Útil cuando la web cambia a diario y la mantiene el propio cliente (p. ej., WordPress).
    Ojo con los apuntes

    Los apuntes lo llaman “Gestor de Contenidos o CRM”. Un gestor de contenidos es un CMS (Content Management System). Un CRM (Customer Relationship Management) gestiona la relación con los clientes, como Salesforce, y en la clasificación siguiente aparece como aplicación empresarial.

    EmpresarialesCRM (Salesforce), gestión de proyectos (Trello, Asana), colaboración (Slack, Teams), recursos humanos (Workday).
    ProductividadGoogle Docs y Office Online, Google Sheets, Evernote, Todoist.

    Noticias y mediosPortales de noticias, blogs y foros.
    Salud y bienestarCita médica online y seguimiento de salud, ejercicio y nutrición.
    Viajes y reservasReserva de vuelos y hoteles; planificación de rutas.

    ModeloCómo divide la aplicaciónPara qué sirveEjemplos

Separa responsabilidades y permite reutilizar código.Frameworks Laravel y Symfony (PHP), Spring MVC (Java), Django (Python), Ruby on Rails. En una tienda online: el modelo es Producto, la vista la página del catálogo y el controlador el que atiende /productos.
    MVVM (Modelo-Vista-Modelo de Vista)Modelo · Vista · ViewModel: intermediario que prepara los datos del modelo para mostrarlos en la vista.Interfaces ricas y muy interactivas.Vue.js y Angular en web; apps de escritorio con WPF (.NET) y apps Android con Jetpack. Por ejemplo, un formulario que se actualiza al escribir.
    MVP (Modelo-Vista-Presentador)Modelo · Vista · Presentador: intermediario que gestiona la lógica de la interfaz.Separar la lógica de presentación de la vista.Apps Android clásicas y aplicaciones de escritorio con Windows Forms (.NET).
    MicroserviciosMuchos servicios pequeños, independientes y autónomos, cada uno con una función.Escalar, desplegar y mantener cada parte por separado.Netflix, Amazon, Uber o Spotify: un servicio para usuarios, otro para pagos, otro para recomendaciones… Suelen ir en contenedores Docker con Kubernetes.

    ServerlessFunciones sueltas que se ejecutan cuando ocurre un evento.El proveedor cloud gestiona los servidores; tú solo escribes código.AWS Lambda, Google Cloud Functions, Azure Functions o Netlify Functions. Por ejemplo, una función que redimensiona una foto cuando se sube.
    Pista

    MVC, MVVM y MVP se parecen: todos tienen Modelo y Vista. Lo que cambia es la pieza del medio: Controlador, ViewModel o Presentador.

    1.5.- Plataformas web libres y propietarias.

    Una plataforma web es el conjunto de software con el que se diseña y se ejecuta un sitio web. Tiene cuatro componentes:

    1. Sistema operativo: la base del equipo. A veces limita qué otros componentes puedes usar.
    2. Servidor web: atiende las peticiones que llegan por Internet. Si la página es estática, devuelve el archivo tal cual; si es dinámica, pasa la petición al programa que la genera.
    3. Gestor de bases de datos: guarda los datos de forma ordenada.
    4. Lenguaje de programación interpretado: controla las aplicaciones del sitio.

    1.6.- Escalabilidad.

    El número de usuarios de una web puede dispararse en muy poco tiempo. Una aplicación es escalable si puede recibir más recursos para atenderlos sin cambiar su comportamiento.

    TipoEn qué consiste
    VerticalMejorar cada nodo (upgrades). Según los apuntes, también separar las capas de la aplicación en máquinas distintas (una máquina por capa), unidas por middleware (software intermedio que las conecta).
    HorizontalAñadir nodos: clonar el sistema en otras máquinas parecidas y repartir el trabajo con un balanceador de carga.
    ClusterAgrupar servidores de aplicaciones para que trabajen como uno solo.
    Ojo con los apuntes

    Fuera de estos apuntes, “escalar verticalmente” suele significar dar más potencia a la misma máquina (CPU, RAM) y “horizontalmente”, añadir más máquinas. Para el examen, quédate también con la idea de los apuntes: vertical = una máquina por capa.

    ¿Qué es un balanceador de carga?

    Imagina un supermercado con una sola caja: cuando llega mucha gente se forma una cola enorme. La solución es abrir más cajas y poner a alguien en la entrada de las colas que diga “tú a la 1, tú a la 2, tú a la 3…”. En una web pasa lo mismo:

    • Las cajas son los servidores: varias máquinas con la misma aplicación instalada (copias o “clones”).
    • La persona que reparte es el balanceador de carga: una máquina o programa que se pone delante de los servidores.
    • La carga es el trabajo: las peticiones que llegan de los usuarios.

    El usuario escribe www.tienda.com y su petición llega al balanceador, nunca directamente a un servidor. El balanceador elige un servidor, le pasa la petición y devuelve la respuesta. El usuario no sabe cuántos servidores hay detrás: para él es una sola web.

                           ┌──► Servidor 1  (copia de la web)
Usuarios ──► BALANCEADOR ──► Servidor 2  (copia de la web)
                       └──► Servidor 3  (copia de la web)

    Para qué sirve:

    • Atender a más usuarios: si se queda corto, se añade otro servidor (eso es la escalabilidad horizontal).
    • Que la web no se caiga: si un servidor se estropea, el balanceador deja de enviarle peticiones y la web sigue funcionando con los demás (alta disponibilidad).

    Cómo decide a qué servidor enviar cada petición

    • Round Robin (por turnos): la 1.ª petición al servidor 1, la 2.ª al 2, la 3.ª al 3, la 4.ª otra vez al 1…
    • LRU (Least Recently Used, el menos usado recientemente): manda la petición al servidor que lleva más tiempo sin recibir trabajo.

    El problema de la sesión

    La sesión es la información que el servidor recuerda de ti mientras navegas: que has iniciado sesión, lo que tienes en el carrito… Normalmente se guarda en la memoria del servidor que te atendió.

    Ejemplo: añades unas zapatillas al carrito y te atiende el servidor 1, que lo apunta en su memoria. Pulsas “Ver carrito” y el balanceador, por turnos, te manda al servidor 2. Ese servidor no sabe nada de ti y te muestra el carrito vacío.

    Hay dos soluciones, y de esto dependen los tipos de balanceador:

    1. Que el balanceador recuerde quién eres y te mande siempre al mismo servidor. Para eso tiene que leer el paquete HTTP, que lleva tu identificador de sesión (por ejemplo, la cookie JSESSIONID en Java). A esto se le llama “mantener la sesión” o sesión pegajosa.
    2. Sacar la sesión del servidor y guardarla en cookies (en tu navegador) o en una base de datos compartida. Así da igual qué servidor te toque, porque todos pueden consultarla.

    Tipos de balanceador (escalabilidad horizontal)

    Ahora la tabla se entiende mejor: la diferencia está en si leen el HTTP (y por tanto pueden mantener la sesión) y en lo rápidos que son. Leer cada paquete lleva tiempo, así que cuanto más “lee”, más lento va.

    BalanceadorCómo funciona¿Mantiene la sesión?Velocidad
    SoftwarePor ejemplo, Apache con el módulo mod_jk. Lee el paquete HTTP, identifica la sesión del usuario y recuerda qué máquina la atiende.✅ Sí: todas las peticiones de una sesión van a la misma máquina.La más lenta
    HardwareReparte según un algoritmo (Round Robin: por turnos; LRU: a la menos usada recientemente). No lee el paquete HTTP; conmuta circuitos.❌ No: la sesión hay que guardarla en cookies o en base de datos.La más rápida
    Hardware HTTPHardware que sí lee el paquete HTTP y mantiene la relación usuario-máquina.✅ SíIntermedia. Es la solución más aceptada hoy.
    Pista

    Software = lee HTTP, recuerda la sesión, lento. Hardware = no lee nada, solo reparte por turnos, rapidísimo, la sesión va en cookies o BD. Hardware HTTP = lo mejor de los dos: lee HTTP y es bastante rápido. Ejemplos reales: Apache (mod_jk, mod_proxy_balancer), Nginx y HAProxy (software); F5 BIG-IP (hardware); y en la nube, AWS Elastic Load Balancing. Al final del tema configuras uno con Apache delante de Tomcat (balancer://tomcat_cluster).

    Cluster

    Un cluster de servidores de aplicaciones reparte la carga de una aplicación normal entre varias máquinas, de forma transparente para el usuario y el administrador. Con la replicación de sesión, cualquier máquina puede acceder a la sesión del usuario (en Java, el objeto HttpSession). A cambio, esa replicación suele causar problemas de rendimiento.

    Autoevaluación

    ¿En qué tipo de escalabilidad se emplean los balanceadores de carga?

    Horizontal. El balanceador reparte las peticiones entre varias máquinas clonadas. Puede ser software (se basa en las sesiones), hardware (se basa en un algoritmo de reparto) o hardware HTTP (un punto intermedio).

    2.- Servidor web Apache.

    Un servidor web es un programa que está siempre en marcha esperando peticiones de los navegadores. Responde con la página pedida o con un mensaje de error. El término también se usa para el ordenador que lo ejecuta.

    Apache es uno de los servidores web más usados. Es gratuito y de código abierto y funciona en Windows, GNU/Linux y otros sistemas. Lo desarrolla la Apache Software Foundation en el proyecto HTTP Server (httpd), con la Licencia Apache, que permite crear derivados tanto abiertos como cerrados.

    Arquitectura: está hecho de módulos

    • Cada módulo agrupa las funciones de un aspecto concreto del servidor.
    • El binario httpd incluye varios módulos ya compilados.
    • Los módulos se activan o desactivan al arrancar el servidor. En Ubuntu se usan a2enmod y a2dismod.
    CategoríaPara qué sirveEjemplos
    Núcleo (core)Funciones esenciales del servidor.mod_mime (tipos MIME), mod_dir (directorios), mod_log_config
    Autenticación y autorizaciónIdentificar usuarios y controlar quién accede a qué.mod_auth_basic, mod_auth_digest, mod_authz_host
    Procesamiento de contenidoEjecutar scripts antes de enviar la respuesta.mod_php, mod_cgi
    SeguridadDefenderse de ataques web.mod_security
    CompresiónComprimir antes de enviar, para que la página cargue antes.mod_deflate
    SSL/TLSConexiones cifradas (HTTPS).mod_ssl
    Registro (logging)Guardar un registro de eventos y actividad.mod_log_config
    CachéGuardar respuestas para servirlas más rápido.mod_cache, mod_mem_cache
    Redirección y reescrituraRedirigir URL y reescribir rutas.mod_rewrite
    Ojo con los apuntes
    • Los apuntes dicen que los módulos de núcleo “no se pueden deshabilitar”. En realidad solo son imprescindibles core y el MPM (el módulo que gestiona procesos e hilos). mod_mime, mod_dir o mod_log_config son módulos base: vienen activados, pero se pueden desactivar.
    • mod_mem_cache ya no existe en Apache 2.4. En su lugar se usa mod_cache_socache.

    Pista

    Dos detalles que suelen caer en el examen:

    • auth vs authz: la z es de autorización. Auth responde a “¿quién eres?” y authz a “¿tienes permiso?”.
    • basic vs digest: basic es la versión básica, con la contraseña casi en claro. Digest “digiere” la contraseña y la convierte en un hash.

    Truco 2: una historia, la discoteca. Imagina que una petición es una persona que quiere entrar en una discoteca y que cada módulo es un empleado:

    1. mod_ssl es el túnel privado por el que llega, para que nadie la espíe.
    2. mod_security es el detector de metales de la entrada.
    3. mod_authz_host es el portero que mira de dónde vienes: “los de esta IP no pasan”.
    4. mod_auth_basic es el portero que pide el DNI y la entrada (usuario y contraseña).
    5. mod_rewrite es el que dice “esa sala está cerrada, ve por la otra puerta”.
    6. mod_dir te lleva a la sala principal si no pides ninguna en concreto (el index).
    7. mod_php es el barman: prepara la bebida en el momento, como el contenido dinámico.
    8. mod_mime pone la etiqueta al vaso: “esto es un cóctel” (text/html).
    9. mod_cache tiene bebidas ya preparadas en la nevera para servir más rápido.
    10. mod_deflate te la da en un vaso pequeño para llevarla más fácil (comprimida).
    11. mod_log_config es la cámara de seguridad que lo graba todo.

    Es aproximadamente el orden en que actúan los módulos en una petición real. Si recuerdas la historia, recuerdas la tabla y además entiendes cómo funciona Apache.

    Truco 3: agrupar las 9 categorías en 4 preguntas. Nueve categorías sueltas cuestan; cuatro grupos, no.

    PreguntaCategoríasMódulos

    2. ¿Puede entrar?SSL/TLS · Seguridad · Autenticación y autorizaciónmod_ssl, mod_security, mod_auth_*, mod_authz_host
    3. ¿Qué le doy?Procesamiento de contenido · Redirección y reescrituramod_php, mod_cgi, mod_rewrite

    2.1.- Instalación y configuración.

    Cómo abrir GitHub Codespaces

    GitHub Codespaces es un Ubuntu en el navegador: no instalas nada en tu portátil y tienes sudo.

    Abrir GitHub Codespaces ↗

    El primer día (solo una vez):

    1. Pulsa el botón de arriba. Si ya tienes el Codespace de PHP, no lo uses: ese no es Ubuntu y Apache, MySQL o Tomcat pueden fallar ahí. Vas a crear otro aparte (puedes tener los dos).
    2. Baja hasta Explore quick start templates → Blank → Use this template. En un minuto se abre VS Code en el navegador con una terminal abajo.
    3. Ponle nombre para no confundirlo con el de PHP: en github.com/codespaces, en tu nuevo Codespace → ··· → Rename → «Despliegue».
    4. Vuelve a la terminal y sigue con los comandos que hay justo debajo (instalar Apache).

    Los demás días: github.com/codespaces → pulsa Despliegue (no crees otro: lo que instalaste está ahí) → en la terminal, arranca los servicios con sudo service apache2 start (no se encienden solos).

    Al terminar: github.com/codespaces → ··· → Stop codespace, para no gastar horas gratis.

    Dos cosas a saber en Codespaces
    • Encender y apagar servicios (Apache, MySQL…): sudo service apache2 start|stop|restart|status. En internet y en la máquina virtual verás systemctl: en Codespaces no funciona, usa siempre service.
    • Ver tu web en el navegador: pestaña Ports (junto a la terminal) → Add Port → 80 (Apache) u 8080 (Tomcat) → icono 🌐.

    Instalación en Ubuntu 22.04 LTS, que puede ser una máquina real, una máquina virtual o un contenedor:

    sudo apt update
sudo apt install apache2

# Para montar una plataforma LAMP, también PHP y MySQL:
sudo apt install php libapache2-mod-php php-mysql
sudo apt install mysql-server

    sudo apachectl configtest      # comprueba la sintaxis → "Syntax OK"

    Si todo está bien, al abrir http://192.168.56.56 (la IP del servidor) verás la página de bienvenida.

    Si sale Syntax OK, la configuración está bien escrita. Si ves un error, te dice el archivo y la línea. Para ver la página, abre el puerto 80 en la pestaña Ports (icono 🌐).

    • Los puertos por debajo de 1024, como el 80, son privilegiados: hace falta ser root para que Apache escuche en ellos.
    • Al arrancar, el proceso principal httpd sigue como root y lanza procesos hijo con menos privilegios, que son los que atienden las peticiones.
    • El demonio httpd se controla con el script apachectl, que prepara las variables de entorno y entiende start, restart y stop. Es el comando genérico de Linux; en Debian y Ubuntu se suele usar systemctl.

sudo systemctl stop apache2       # parar
sudo systemctl restart apache2    # reiniciar
sudo systemctl start apache2      # arrancar

    Para encender, apagar o reiniciar Apache en tu Codespace:

    sudo service apache2 status     # estado
sudo service apache2 stop       # parar
sudo service apache2 restart    # reiniciar
sudo service apache2 start      # arrancar

    Si buscas en internet verás systemctl en lugar de service: en Codespaces systemctl da error (System has not been booted with systemd), usa siempre service. Después de tocar un archivo de configuración, haz restart.

    Reflexiona

    ¿Hay que reiniciar Apache si, al crear un host virtual, cambias el puerto de escucha? Sí. Apache solo lee la configuración al arrancar o reiniciar. Recuerda añadir el puerto nuevo con Listen en ports.conf.

    3.- Aplicaciones web y servidores de aplicaciones.

    Una aplicación web es una aplicación cliente-servidor que se ejecuta en un entorno web:

    Clientenavegador
    Comunicaciónprotocolo HTTP
    Servidorservidor web

    Un servidor de aplicaciones es el software (o la máquina) que ejecuta aplicaciones para los clientes, normalmente a través de HTTP, y gestiona casi todo el acceso a los datos. Se diferencia de un servidor web en que trabaja sobre todo con contenido dinámico y suele estar integrado con bases de datos.

    VentajaPor qué
    Centralización y menos complejidadLas aplicaciones no se programan desde cero: se ensamblan con bloques que ofrece el servidor.
    Integridad de datos y códigoTodo está en una o pocas máquinas, así que una actualización llega a todos los usuarios a la vez.

    El término se usa en todas las plataformas: comercio electrónico, gestores de contenido, constructores de webs…

    Ejemplo: Jakarta EE (antes Java EE)

    La plataforma Java Enterprise Edition ahora se llama Jakarta EE y la dirige la Eclipse Foundation. Se organiza en niveles:

    Nivel Clientenavegador / aplicación cliente
    Nivel Medio · WebJSP, Servlets (contenedor web)
    Nivel Medio · NegocioEnterprise Beans (contenedor EJB)
    Nivel EISbases de datos, archivos, aplicaciones existentes

    El nivel medio es la propia plataforma: un servidor web y un servidor EJB (Enterprise JavaBeans), también llamados contenedores. EIS significa Enterprise Information System (Sistema de Información Empresarial).

    3.1.- El servidor de aplicaciones Tomcat.

    Tomcat (Apache Tomcat) hace dos cosas: es servidor web, porque atiende peticiones y respuestas HTTP, y es servidor de aplicaciones, o mejor dicho, contenedor de Servlets y JSP. Incluye el compilador Jasper, que convierte las JSP en servlets.

    Ojo con los apuntes

    Los apuntes dicen que Tomcat “incluye el servidor Apache”. No es así: Tomcat tiene su propio conector HTTP (llamado Coyote), escrito en Java. Apache HTTP Server (httpd) es otro programa que se puede poner delante de Tomcat (ver el proxy inverso en 3.1.2). Los dos son de la Apache Software Foundation; de ahí la confusión.

    Un contenedor de servlets es el entorno (shell) que carga y ejecuta los servlets en nombre del usuario. Hay tres tipos según cómo se relacionan con el servidor web y la JVM (Máquina Virtual de Java):

    TipoCómo funcionaPros / contras
    1. Stand-alone (independiente)El contenedor forma parte del propio servidor web, que está hecho en Java. Es el modo por defecto de Tomcat.Sencillo, pero la mayoría de servidores web no están hechos en Java.
    2. Dentro de procesoUn plugin del servidor web abre una JVM dentro del proceso del servidor y le pasa las peticiones de servlets mediante JNI.Buen rendimiento, pero escala poco. Adecuado para servidores multihilo de un solo proceso.
    3. Fuera de procesoLa JVM se ejecuta fuera del servidor web. El plugin y la JVM se comunican por IPC, normalmente sockets TCP/IP.Responde algo más lento, pero gana en escalabilidad y estabilidad.

    Tomcat puede usarse solo (sobre todo para desarrollar y depurar) o como plugin de otro servidor web (Apache, IIS). En los modos 2 y 3 hace falta instalar además un adaptador para el servidor web.

    Autoevaluación

    Las funciones del Servidor Apache y las funciones del servidor Tomcat, ¿son equivalentes?

    No. Apache es solo un servidor web, mientras que Tomcat es un servidor de aplicaciones (contenedor de servlets y JSP).

    3.1.1.- Instalación y configuración básica.

    Para cualquier versión de Tomcat hace falta el JDK (Java Development Kit).

    1. Instalar Java

    sudo apt update
sudo apt install default-jdk

    2. Crear el usuario y el grupo tomcat

    El usuario tiene como carpeta personal /opt/tomcat, donde instalaremos Tomcat, y como shell /bin/false, para que nadie pueda iniciar sesión con esa cuenta. Así Tomcat no se ejecuta como root.

    sudo groupadd tomcat
sudo useradd -s /bin/false -g tomcat -d /opt/tomcat tomcat

    3. Descargar y descomprimir Tomcat 9

    cd /tmp
curl -O https://archive.apache.org/dist/tomcat/tomcat-9/v9.0.96/bin/apache-tomcat-9.0.96.tar.gz
sudo mkdir /opt/tomcat
sudo tar xzvf apache-tomcat-*tar.gz -C /opt/tomcat --strip-components=1

    --strip-components=1 quita la carpeta apache-tomcat-9.0.96/ del principio, para que el contenido quede directamente en /opt/tomcat. Si no tienes curl: sudo apt install curl.

    4. Permisos

    cd /opt/tomcat

    3.1.2.- Administrar Tomcat.

    Tomcat escucha en el puerto 8080 y despliega lo que hay en $CATALINA_HOME/webapps. Puedes comprobarlo en /opt/tomcat/conf/server.xml:

    Crear un usuario administrador

    Para usar las aplicaciones de administración (manager-gui y admin-gui), añade un usuario en /opt/tomcat/conf/tomcat-users.xml, dentro de <tomcat-users>. Usa una contraseña segura:

    <tomcat-users . . .>

</tomcat-users>

    Permitir el acceso desde otra máquina

    Por defecto, las aplicaciones de administración solo aceptan conexiones desde el propio servidor. Para entrar desde tu PC, edita la válvula (RemoteAddrValve, un filtro de IPs) en webapps/manager/META-INF/context.xml y webapps/host-manager/META-INF/context.xml. Si quieres ver también la documentación y los ejemplos, haz lo mismo en docs y examples.

    <Context antiResourceLocking="false" privileged="true" >
  <Valve className="org.apache.catalina.valves.RemoteAddrValve"
         allow="127\.\d+\.\d+\.\d+|::1|0:0:0:0:0:0:0:1|192\.168\.56\.\d+" />
</Context>

    allow es una expresión regular. Aquí añade 192\.168\.56\.\d+, es decir, cualquier IP de la red 192.168.56.x.

    Tomcat solo deja entrar al gestor desde el propio servidor, por seguridad. En Codespaces normalmente no tienes que tocar nada: lo que abres desde la pestaña Ports le llega a Tomcat como si viniera del propio servidor. Solo si al entrar al gestor sale 403 Access Denied, abre code /opt/tomcat/webapps/manager/META-INF/context.xml y pon <!-- antes de <Valve y --> después de su /> (eso “desactiva” el filtro).     Debes conocer: proxy inverso

    Un proxy inverso se pone delante de uno o varios servidores backend, que son los que generan el contenido y no suelen estar expuestos a Internet. Recibe la petición del cliente, la reenvía a un backend y devuelve la respuesta como si fuera suya. Para el cliente, es la única fuente del contenido. También se le llama servidor de paso o gateway.

    Para qué sirve: seguridad (el backend queda aislado), alta disponibilidad, balanceo de carga y autenticación centralizada.

    Clientenavegador
    Apacheproxy inverso, puerto 80
    Tomcatbackend, AJP 8009 / HTTP 8080

    Para que Apache haga de proxy de Tomcat, activa estos módulos y reinicia:

    sudo a2enmod proxy
sudo a2enmod proxy_ajp
sudo a2enmod proxy_balancer
sudo systemctl restart apache2
    sudo a2enmod proxy
sudo a2enmod proxy_ajp
sudo a2enmod proxy_balancer
sudo service apache2 restart     # reiniciar Apache para cargar los módulos

    a2enmod activa un módulo de Apache. El bloque <Proxy balancer://…> de abajo se escribe igual (con code y Retry as Sudo). Para probarlo, abre el puerto 80 (Apache) en Ports: debería salir lo que sirve Tomcat.

    AJP (Apache JServ Protocol) es un protocolo interno muy rápido con conexiones TCP persistentes. Se usa para comunicar Apache con Tomcat; también valdría HTTP contra el puerto 8080. El conector AJP de Tomcat escucha en el 8009, y se puede cambiar en /opt/tomcat/conf/server.xml.

    En el host virtual /etc/apache2/sites-enabled/000-default.conf añade:

    <Proxy balancer://tomcat_cluster>
  Order allow,deny
  Allow from all
  BalancerMember ajp://localhost:8009
</Proxy>
ProxyPreserveHost On
ProxyPass /phpmyadmin/ !
ProxyPass / balancer://tomcat_cluster/
ProxyPassReverse / balancer://tomcat_cluster/
    DirectivaQué hace
    <Proxy balancer://tomcat_cluster>Define un cluster llamado tomcat_cluster.
    BalancerMember ajp://localhost:8009Añade un miembro al cluster: protocolo, IP y puerto.
    ProxyPreserveHost OnMantiene la cabecera HTTP Host original en vez de reescribirla.
    ProxyPass /phpmyadmin/ !El ! significa “esto no se pasa a Tomcat”: lo sirve Apache.
    ProxyPass / balancer://tomcat_cluster/Todo lo que cuelga de / se envía al cluster de Tomcat.
    ProxyPassReverseCorrige las cabeceras de las respuestas (redirecciones) para que apunten a Apache y no a Tomcat.

    Por último, cambia en ese archivo el DocumentRoot y <Directory /var/www/html> para que apunten a /var/www/ROOT. Así decides desde un solo directorio qué parte gestiona cada aplicación.

    Ojo con los apuntes
    • Order allow,deny y Allow from all son sintaxis de Apache 2.2. En Apache 2.4 (el de Ubuntu 22.04) solo funcionan con mod_access_compat. Lo actual es Require all granted.
    • Desde Tomcat 9.0.31, el conector AJP del puerto 8009 viene comentado en server.xml. Hay que descomentarlo y configurar secretRequired/secret; si no, Apache no podrá conectar por AJP.
    • Los apuntes usan /etc/init.d/apache2 restart; funciona, pero en Ubuntu lo habitual es systemctl restart apache2.

    4.- Estructura y despliegue de una aplicación web.

    Una aplicación web Java está formada por servlets, páginas JSP, HTML, imágenes, sonidos, clases… Todo esto se puede empaquetar y ejecutar en distintos contenedores.

    Un servlet es un programa Java que realiza un servicio concreto dentro de un servidor web: recibe una petición y genera una respuesta. La especificación Servlet 2.2 define la estructura de carpetas:

    • El directorio raíz lleva el nombre de la aplicación y es la raíz de documentos.
    • Todo lo que hay bajo la raíz se puede servir al cliente, excepto META-INF y WEB-INF, que son privados.
    • Los archivos privados, como los .class de los servlets, van en WEB-INF.

    Mientras se desarrolla, se trabaja con las carpetas. Para producción, todo se empaqueta en un archivo .war.

    /index.jsp
/WebContent/jsp/welcome.jsp
/WebContent/css/estilo.css
/WebContent/js/utils.js
/WebContent/img/welcome.jpg
/WEB-INF/web.xml
/WEB-INF/struts-config.xml
/WEB-INF/lib/struts.jar
/WEB-INF/classes/com/empresa/proyecto/action/welcomeAction.class
    Ojo con los apuntes

    En el ejemplo pone classess; la carpeta se llama WEB-INF/classes. Además, WebContent es la carpeta del proyecto en Eclipse: al empaquetar el WAR, su contenido se copia directamente en la raíz.

    De forma genérica, una aplicación web tiene tres capas:

    1. Navegador webcliente
    2. Tecnología web dinámicaPHP, Java Servlets, ASP…
    3. Base de datosguarda la información de forma permanente

    4.1.- Archivos WAR.

    WAR = Web Application Archive (Archivo de Aplicación Web). Es un único archivo con una aplicación web Java completa: servlets y JSP, contenido estático (HTML, imágenes…) y otros recursos. Por dentro es un ZIP con una estructura concreta.

    Ventajas:

    • Despliegue más sencillo: basta con un archivo por servidor del cluster.
    • Más seguridad: una aplicación web no puede acceder a otra.
    CarpetaContenido
    /Raíz: HTML, JSP y CSS (*.html, *.jsp, *.css). Se pueden pedir desde el navegador.
    /WEB-INF/Configuración: página de inicio, ubicación de los servlets, parámetros… El archivo más importante es web.xml.
    /WEB-INF/classes/Clases Java compiladas, normalmente los servlets.
    /WEB-INF/lib/Librerías JAR: conexión a la base de datos, librerías de JSP…

    Herramientas para generar un .war

    TipoHerramientas
    IDENetBeans y Eclipse (open source), IntelliJ IDEA.
    AutomatizaciónAnt (open source; no es un IDE, es el “make de Java”), Apache Maven y Gradle.

    Un archivo .WAR…

    4.2.- Despliegue de aplicaciones con Tomcat.

    Las dos formas más sencillas:

    1. Copiar el .war en $CATALINA_HOME/webapps

    El usuario tomcat tiene que poder abrir el archivo. Por eso primero se cambia su dueño y luego se copia con -p, que conserva dueño y permisos:

    sudo chown tomcat:tomcat sample.war
sudo cp -p sample.war /opt/tomcat/webapps

    Tomcat detecta el .war solo y lo despliega: lo descomprime en webapps/sample/. Pruébalo en http://<IP>:8080/sample. El nombre del archivo es la ruta de la aplicación.

    2. Desde el gestor web (/manager)

    Entra en http://<IP>:8080/manager. En la sección “WAR file to deploy”, selecciona el archivo y pulsa Deploy.

    1. Copiar el .war en la carpeta webapps de Tomcat. Si ya lo descargaste en el apartado 4.1, sáltate las dos primeras líneas. chown hace que el archivo sea del usuario tomcat (si no, Tomcat no puede abrirlo) y cp -p lo copia conservando ese dueño:

    cd ~
curl -O https://tomcat.apache.org/tomcat-9.0-doc/appdev/sample/sample.war
jar -tf sample.war                           # ver su contenido
sudo chown tomcat:tomcat sample.war
sudo cp -p sample.war /opt/tomcat/webapps    # Tomcat lo despliega solo

    Tomcat lo detecta solo y lo descomprime en webapps/sample/. Ábrelo con el puerto 8080 de Ports añadiendo /sample/ al final de la dirección. El nombre del archivo es la ruta de la aplicación.

    2. Desde el gestor web. Entra en tu dirección del 8080 + /manager/html → sección WAR file to deploy → Seleccionar archivo (lo eliges desde tu Mac) → Deploy.

    4.3.- Descriptor de despliegue.

    El descriptor de despliegue es un documento XML que describe cómo se despliega una aplicación, un módulo o un componente. Es declarativo: puedes cambiar la configuración sin tocar el código fuente.

    ArchivoQué es
    WEB-INF/web.xmlDescriptor de cada aplicación. Toda aplicación web debe tenerlo.
    $CATALINA_HOME/conf/web.xmlDescriptor por defecto de Tomcat. Se aplica antes que el de la aplicación y solo debe tener configuración general.
     
    <?xml version="1.0" encoding="ISO-8859-1"?>
<!DOCTYPE web-app PUBLIC
  "-//Sun Microsystems, Inc.//DTD Web Application 2.2//EN"
  "http://java.sun.com/j2ee/dtds/web-app_2_2.dtd">
<web-app>
  <!-- Tus definiciones van aquí -->
</web-app>

    Dentro de <web-app> se declaran los servlets, con las etiquetas en este orden:

    <servlet>
  <servlet-name>nombre</servlet-name>
  <servlet-class>package.nombre.MiClass</servlet-class>
</servlet>
    • servlet-name: nombre interno que le das al servlet.
    • servlet-class: clase Java que lo implementa, con su paquete.

    Para probarlo, con Tomcat arrancado: http://{address}:{port}/{servletName}; por ejemplo, http://<IP>:8080/sample.

    Ojo con los apuntes

    Con solo <servlet>, el servlet no tiene URL. Hace falta también un <servlet-mapping> que lo asocie a una ruta. La URL real es http://IP:puerto/aplicación/url-pattern. En el ejemplo, /sample es el nombre de la aplicación, no del servlet.

    <servlet-mapping>
  <servlet-name>nombre</servlet-name>
  <url-pattern>/hola</url-pattern>
</servlet-mapping>
<!-- → http://IP:8080/sample/hola -->

    Autoevaluación · tecnologías asociadas a aplicaciones

    La Interface Común de Entrada es uno de los estándares más antiguos en Internet para trasladar la información desde una página web a un servidor web:

    CGI (Common Gateway Interface).

    Las Hojas de Estilo en Cascada se usan para formatear las páginas web:

    CSS (Cascading Style Sheets).

    Las Páginas Activas se ejecutan del lado del servidor:

    ASP (Active Server Pages).

    Este lenguaje es, como ASP, usado en el lado del servidor, es similar a ASP y puede ser usado en circunstancias similares:

    PHP (Hypertext Preprocessor).

    Algo así como lenguaje práctico de extracción y de informes, nace con el objetivo principal de simplificar las tareas de administración de un sistema UNIX:

    Perl (Practical Extraction and Report Language). Es el lenguaje con el que se escribían muchas rutinas CGI.

    Errores comunes del tema

    ❌ Error✅ Corrección
    “El protocolo de la web es HTML.”El protocolo es HTTP; HTML es el lenguaje de las páginas.
    Confundir CMS con CRM.CMS = gestor de contenidos (WordPress). CRM = gestión de clientes (Salesforce).
    “Apache y Tomcat hacen lo mismo.”Apache es servidor web; Tomcat es servidor de aplicaciones (contenedor de servlets/JSP), aunque también sirve HTTP.
    “El balanceador hardware mantiene la sesión.”El hardware puro no lee HTTP y no la mantiene (sesión en cookies o BD). El software y el hardware HTTP sí.
    Balanceadores = escalabilidad vertical.Son de escalabilidad horizontal (más nodos).
    Editar apache2.conf y no ver los cambios.Hay que reiniciar o recargar: sudo systemctl restart apache2. Antes, apachectl configtest.
    Crear el .conf del host virtual y esperar que funcione.Hay que activarlo con a2ensite y recargar Apache.
    Buscar Tomcat en el puerto 80.Tomcat usa el 8080 (HTTP) y el 8009 (AJP). El 80 es de Apache.
    Crear el tomcat.service y hacer start directamente.Primero sudo systemctl daemon-reload, para que systemd lea el archivo nuevo.
    Error 403 al entrar en /manager desde tu PC.Añade tu red al allow de la RemoteAddrValve en manager/META-INF/context.xml, y crea el usuario con rol manager-gui.
    Copiar el .war con cp sin cambiar el dueño.chown tomcat:tomcat y después cp -p, para que el usuario tomcat pueda leerlo.
    Poner archivos privados o .class en la raíz del WAR.Van en WEB-INF/ (clases en WEB-INF/classes, JAR en WEB-INF/lib): no se pueden pedir desde el navegador.
    Declarar el servlet en web.xml sin <servlet-mapping>.Sin mapping no tiene URL. La URL es /aplicación/url-pattern.
